# OTE Vancity Payment Helper

The extension source lives in this repo under `extensions/vancity-payment-helper`. It checks contacts, creates missing recipients, selects a saved source account when configured, and prepares payment forms. Prepare opens the bank's Review after receipt capture is ready. **The final payment Send or Confirm remains manual.**

Use **Settings** at the top right for the OTEManager URL and connection, automatic receipt recording, export imports, security question/answer, default source account, and bank navigation. **Payments** contains the volume, issue, student/article search, grouping, and payment choice together. Connecting or importing returns to Payments; switching views preserves the current payment and unsaved preset edits and masks the answer again.

## Build and install

Run `npm run payment-helper:package`. This copies the source to the ignored `public/payment-helper` folder and writes `public/ote-payment-helper.zip` and `artifacts/ote-payment-helper.zip`. Packaging also runs before the app's dev and production builds. Payment Manager offers the same helper as a ZIP download.

In Chrome, open `chrome://extensions`, enable Developer mode, choose **Load unpacked**, and select this `extensions/vancity-payment-helper` folder (the folder containing `manifest.json`). Pin the extension. For updates, replace an existing unpacked copy with the new files and click its **Reload** button. Loading directly from this repo means future source updates only require Reload.

The permissions are `activeTab`, `scripting`, `storage` and, from v0.12, `sidePanel` for the helper window. Chrome 116 or newer is required. Clicking **Connect to OTEManager** requests optional permission only for the OTEManager URL you enter. From v0.12.1, **Connect Vancity** separately requests optional access only to `https://my.vancity.com/*` so the sidebar can read the bank tab and prepare forms after temporary `activeTab` access expires. Chrome asks before granting new site access. No site access is granted merely by installing the update. The popover can also use temporary `activeTab` access when invoked directly on the bank tab. A Manifest V3 service worker handles bank receipt messages and write-back while the popup is closed. This extension has not been reviewed by Vancity or the Chrome Web Store.

## Sidebar or popover (v0.12)

The toolbar opens a **Sidebar** by default, keeping the helper beside Vancity. Under **Settings → Helper window**, choose **Sidebar** or **Popover** and save. Close the current helper and click its toolbar icon again to use the new preference. Both windows use the same saved payments, presets and receipts; the full workspace remains available. The sidebar permission does not add access to bank accounts or additional sites. This follows the same saved-window pattern as ACtools.

The bank tab stays pinned while a payment is waiting for confirmation. Open the sidebar beside Vancity and choose **Connect Vancity**, then accept Chrome's prompt for that exact bank site. Once allowed, the button becomes **Use this Vancity tab**. If you open a different bank tab, use that button after completing the pending payment. This also updates the automatic-next setting's bank tab when no payment is pending. If the previously connected tab closed and no payment is pending, preparation can reconnect to the active Vancity banking tab in the last focused browser window. Hidden URL metadata and revoked script access explain that Vancity needs connecting instead of incorrectly saying the bank is not open.

**Settings → Helper window → Remove Vancity site access** revokes that optional bank grant and stops automatic preparation. It keeps the saved presets, receipt journal and any pending payment details. This is independent of the OTEManager connection. On Review, preparation controls are paused to prevent opening another transfer, while Settings, confirmation checking and history matching remain available. The helper explains the pending state beside those controls.

Version 0.12.2 verifies the complete value in Review's uniquely labeled Amount row, including a nested currency symbol. A matching service fee, balance or cached amount input cannot substitute for the displayed transfer amount. The displayed email and message also take precedence over cached form values. Switching browser tabs does not move an existing pending payment to a different bank tab.

## Live connection (v0.8)

In **Settings**, enter your hosted OTEManager URL (or `http://localhost:PORT`) and click **Connect to OTEManager**. Accept Chrome's site-access prompt. The helper remembers the URL, opens or reuses the matching Payment Manager tab, and loads current unpaid payments through the app's normal signed-in server connection. If needed, sign in on that tab, then click **Refresh payments**. No payment export or Preview click is needed. Other HTTPS OTEManager deployments are supported when they include this repo's updated page bridge; the bank URL and insecure remote HTTP URLs are rejected.

Choose **Volume**, **Issue**, **Student or article**, and **Transfer grouping**, then choose **Payment to prepare**. Separate transfers per article is the default. Search applies with Refresh or Enter. Filters and the selected payment stay in the browser session. The payment list refreshes every minute while the helper workspace is visible and idle, and is freshly checked before Prepare. A changed or paid record stops before any bank preparation; review the new details before preparing again. Zero matches shows an empty list rather than leaving stale payment details visible. Any excluded records are counted; amounts still require review in Payment Manager first.

Once a form has been prepared, automatic list refresh pauses until its bank confirmation is captured. The prepared receipt snapshot remains independent of the payment dropdown. Receipt write-back uses only the original OTEManager origin, including the local port. If its page reloads or closes, the worker reconnects that same permitted site and retries through the backend's current-record checks. Failed write-backs remain saved for **Retry OTEManager write-back**; retrying never sends money again. Changing to another site cannot redirect an old site's receipt.

**Disconnect live payments** stops live loading and revokes the selected site's optional permission. It retains saved bank receipts and the remembered URL. **Use an export instead** keeps the older direct-import/file workflows available. Security answers, bank accounts, and server credentials are never sent as part of live payment-list requests.

## Payment workflow

1. Review amounts in OTEManager's Payment Manager. Filter by volume, issue, author or article. Choose separate transfers per article (default), or combined transfers per author. Preview and export selected transfers; incomplete and ineligible records are excluded. Exporting never marks records paid.
2. Sign into Vancity and click the extension on any banking screen. Import the payment JSON, or use **Paste payment JSON instead**. **Go to e-transfer contacts** navigates from Home or Accounts through e-Transfers to Send money. **Open full payment workspace** opens a normal extension tab connected to that bank tab, so the workflow can continue without keeping a small popup open. If the connected bank tab closes or leaves Vancity, actions stop.
3. Optionally choose **Check all recipient emails first**. It searches each unique email and shows found, missing or ambiguous results. This does not create contacts or prepare payments. Keep the popup open during the check; Stop ends it after the current lookup. Completed results remain in session memory.
   Version 0.9 offers **Create N missing contacts** after that scan. This is a separate optional action. In live mode it refreshes the current payment list first, then rechecks each previously missing email. An email added since the scan is skipped. A real missing contact is saved with the configured question/answer when the bank requires them, and its exact email is searched again to verify creation. The batch ends on the contact list, without opening/filling any payment or arming a receipt watcher. Multiple exact matches are left for manual selection. Conflicting OTE names sharing an email are excluded from bulk creation. **Stop after this contact** finishes the current save/verification before stopping. The first bank error stops the queue, with completed results retained; review the current bank screen, fix the issue, then scan again. Use the full workspace while a batch runs. A synthetic recipient is never saved. Chrome Reload can clear session scan results, so scan again after an extension update.
4. Select a payment and click **Prepare this payment · check or create**. There is no extra review checkbox or character counter. Any warnings remain visible; the bank's final payment review is your approval step.
5. If exactly one contact matches the email, the extension opens that recipient's Send money form and fills the saved amount, article description, and any saved question and answer required by the bank. A different display name is permitted only when the email is an exact match. Multiple matches require manual selection.
6. If the email is missing, the extension opens Add contact, fills its name/email and any required saved question and answer, clicks the contact's Continue, verifies the contact review, and clicks its Add contact or bank-specific Confirm button. It recognises Vancity's separate contact-success popup and uses **Back to e-Transfers** to close it. Once the bank confirms creation, it searches the exact email again, opens the saved recipient, and fills the payment. Prepare can also resume from that contact-success popup after an interrupted run. It never uses this contact-confirmation logic on a payment review screen. If Vancity requires extra verification or its review is not recognised, the flow stops with a specific message.
   Synthetic addresses (`.test`, `.invalid`, `.localhost`, `.example`, and the reserved example.com/net/org domains) are filled for preview only and are never saved. Use a real Payment Manager export for automatic contact creation.
7. With a saved default source account, Prepare selects its exact account number before filling payment fields. Without a saved preference, it uses Vancity's selected account. Check the source account, bank's registered recipient/Autodeposit name, amount, date and message. Prepare starts receipt capture, verifies the completed form, clicks the payment's Continue, and verifies the Review email, amount and message. Review and use the final Send or Confirm yourself. Individual **Fill payment amount and message** fills the form and starts receipt capture without advancing. Messages above 400 characters must be shortened in the helper; the exported full description is retained.
8. Before Prepare opens Review, the helper watches the connected bank tab for the **Your transfer has been sent** receipt. It requires a send-success dialog (not contact creation or payment review), an exact recipient email, amount, included-article total, and the message that was actually prepared. The 20-digit reference and receipt are saved on this device. In connected mode, the matching receipt automatically marks all included articles paid and saves the reference in OTEManager. Only the source account's last four digits are retained; security answers are never part of a receipt. A JSON-file import captures the receipt without updating OTEManager. The manual session checklist remains available as a fallback and never writes back.

Individual steps remain available in an expandable section. The helper refuses to navigate away from an unfinished contact or payment form, overwrite conflicting existing values, select ambiguous contacts, or operate outside `https://my.vancity.com/banking/`.

## Direct import from local OTEManager

Open the helper on Vancity once to connect that bank tab. Then open OTEManager's Payment Manager on `localhost` or `127.0.0.1`, choose the desired filters/grouping, click **Preview export**, and select the payments. Open the extension from that OTEManager tab and choose **Import from OTEManager**. The selected preview is imported directly into session storage. **Open full payment workspace** continues on the connected Vancity tab without downloading JSON. The updated hosted OTEManager page is supported too.

This uses the existing `activeTab` permission: click the helper on the OTEManager tab to grant that page access, and on Vancity to grant bank access. It adds no persistent host permissions or externally-connectable web commands. The page supplies its selected export and a connection marker through inert JSON elements. Bank scripts and presets are never sent to OTEManager. The extension validates the export and rechecks that its connected tab is still Vancity before preparing a payment. Changing filters or grouping clears the page preview; preview again before importing.

## Duplicate contact names (v0.9.1)

If Vancity rejects the name because it already exists, the helper tries the name with ` 2`, then ` 3`, and so on, waiting for the bank to validate each candidate. It changes names only in response to the name field's specific duplicate-name error, up to 100 candidates. The added suffix stays within Vancity's 35-character name limit. The accepted bank display name is checked on contact review and reported in the contact results; recipient matching and final verification still use the exact email. OTEManager's author name is unchanged. A resumed editable contact form can retain a numbered name produced from that author's original name. Other validation errors stop the flow instead of triggering name changes.

## Automatic receipt recording in connected mode (v0.7)

Direct import from an updated Payment Manager enables **Automatically record sent payments in connected OTEManager**. Keep that OTEManager tab open with its original selected preview while preparing and sending. Prepare opens payment Review automatically; you still click the bank's final Confirm yourself. The bank-page watcher continues when the helper popup closes; it stops after capture or 30 minutes. If the bank page reloads or a receipt was missed, reopen the helper and choose **Check bank confirmation** while the bank receipt is still visible. The prepared payment's identity is saved separately from the current dropdown selection, so selecting another payment cannot redirect its receipt.

The OTEManager page calls its existing application server. One Convex transaction rechecks every included article's current author, preferred recipient email, eligibility, approval status, publication, title, and saved amount. It records Paid, a dedicated Vancity reference and the receipt together, with an article note. If any included article changed or was already paid, no articles in that transfer are changed. The same reference and payment can be retried without adding duplicate notes; a reference associated with other articles or amounts is rejected. The backend records the helper's observed bank receipt; it does not independently verify a transaction with Vancity's API. Here Paid means a confirmed send, not confirmed recipient deposit. A bank Pending transfer can still be awaiting deposit. Cancelled, expired, or returned transfers require reconciliation in OTEManager; the helper does not track those later bank status changes.

If the app tab is closed, reloaded, signed out, or unavailable, the bank receipt stays saved and the helper shows **Write-back pending**. Reopen the **same** OTEManager environment, open the helper there, choose **Reconnect this OTEManager tab for receipt retries**, then **Retry OTEManager write-back**. A localhost receipt cannot be silently redirected to the hosted site or another local port. Retrying never sends money; a successful retry can prepare the next article when automatic preparation remains enabled. **Download saved receipts** exports the durable journal. These controls remain available without an imported batch, including after browser restart.

### Check an existing Sent transfer (v0.12)

In Vancity, open **e-Transfers → Sent** and open the transfer details. In **After sending in Vancity**, choose **Match open Sent transfer**. This reads that open detail without navigating or changing the bank transfer. It matches the exact email, amount, full article message, transaction date/minute, and source account's last four digits against saved original send receipts. A unique match stores the observed bank status with that local receipt and clears only an identical stale pending-payment context. Successfully synced receipts say **Already recorded in OTEManager**, rather than asking for reconciliation. Failed write-backs can still be retried using the original saved receipt.

Vancity's Accounts debit reference can differ from its original send-confirmation reference. The helper retains the original receipt reference. Sent details without a matching saved receipt cannot supply a missing original reference or automatically create a new Paid record. Multiple matching receipts require attention. A Cancelled, Expired, Declined or Returned status is reported for manual reconciliation; history matching does not change the article's payment status. Pending remains a confirmed send awaiting deposit, not a new payment to prepare.

The app and backend receipt support were deployed to the hosted site on October 13, 2026. Live browsing additionally needs the v0.8 app bridge. An older page can still import payments but reports that a live-connection update is needed. The helper never marks a payment paid from a success message alone, a contact-save popup, or a manually typed reference.

## Automatically prepare the next article (v0.11)

In **Settings → After each recorded payment**, enable automatic preparation, choose **Volume 33 / Issue 2** (the defaults), and save. This requires live OTEManager payments, automatic receipt recording, and a connected Vancity tab. The option also applies to an already-prepared Review for that same issue. You can switch it off with **Stop automatic preparation** on Payments.

After you click Vancity's final Confirm, the helper captures the matching receipt and waits for OTEManager to confirm that it saved the payment. It then requests a fresh list for the configured issue, using **separate transfers per article**, and selects the first remaining unpaid article in OTEManager's order. It excludes articles with any saved bank receipt, including failed write-backs, and articles recorded in the session checklist. The worker verifies and closes only the matching recorded send receipt, checks or creates the next recipient, applies saved account and security presets, starts receipt capture, and opens the next payment's **Review**. **Every final Send or Confirm is yours.** The popup can stay closed, but the signed-in bank tab and original OTEManager connection must remain available.

If a payment was already recorded before you enabled this option, choose **Prepare next unpaid article now** on Payments to start from the most recently recorded receipt in that issue. Preparing another payment manually through the helper also starts the sequence. Existing pending payments must be finished or reconciled first. Changing the issue or site stops the previous scope from continuing automatically.

No remaining eligible articles ends the sequence. A warning, bank validation, sign-in prompt, or interrupted preparation stops it for attention. Stop finishes the current bank step and prevents subsequent steps. Each receipt has a durable preparation claim: extension restarts and duplicate receipts cannot replay bank steps. After an interrupted bank step, inspect Vancity and use the normal **Prepare this payment** for the selected article. A failed write-back retains the receipt; retrying it can start the next preparation only when this option remains enabled for the original issue, site, and bank tab. It never resends the recorded payment.

## Security question and answer

Open **Settings → Security question and answer**. Enter the reusable question (up to 40 characters) and answer (up to 25 characters), then choose **Save question and answer**. They are saved in extension-local storage on this device, without encryption, cloud sync, a passphrase, or an unlock step. The saved answer stays masked in the field. Choose **Show answer** to check it, then **Hide answer** to mask it again. Saving or reopening the helper masks it automatically. Edits show **Unsaved changes** until saved. The saved pair is available after browser restarts and extension updates. **Remove saved question and answer** clears it.

Version 0.4 removes the previous encrypted preset and its session copy when the helper opens. Enter the question and answer once in the new settings. Answers are not included in the extension source, payment exports, or download ZIP.

The extension fills security fields **only when they are visible and editable in Vancity**. It waits for account and amount updates, writes one current security field at a time, and waits for the retained values and enabled Continue to remain stable before reporting success. Prepare repeats this check after receipt capture starts and repairs a blank answer before opening Review. If an existing contact supplies a prior question but leaves its answer blank, the saved preset replaces that question and fills the answer together. A completed conflicting question/answer or a different nonempty answer stops preparation. Hidden fields on Autodeposit recipients remain untouched. Bank validation and the current bank screen remain authoritative; OTE's recorded Autodeposit flag is advisory. Communicate the security answer to recipients yourself.

## Default source account

Open a Vancity Send money form, then open **Settings → Default source account** in the helper. **Remember Vancity's selected account** saves the current source account immediately. Alternatively, **Read accounts from Vancity** opens the bank's account picker, reads its available choices and current balances, and cancels the picker without selecting an account. Choose an account in the helper and click **Save default account**.

The helper saves only the account number, name and type on this device. Balances are shown from the current bank screen and are not persisted. Prepare and Fill payment select the saved account by its exact number, confirm only the account selection, and then fill the payment details. This order matters because Vancity can reset the amount and message when the account changes. A missing or ambiguous account stops preparation; it never chooses a substitute.

**Remove helper's default account** returns to using Vancity's selected account. Vancity also offers its own **Set as default** option in the account picker. The helper's setting is independent and does not change that bank preference. Prepare opens payment Review using Continue after receipt capture is ready; it never clicks the final Send or Confirm.

## Data and limits

Imported payment data, edited messages, contact-check results, the connected tab and the prepared receipt context use `chrome.storage.session`, with no cloud sync. Captured bank receipts use `chrome.storage.local`, survive browser restart, and continue blocking re-preparation of their included articles. This journal includes recipient/payment details and the prepared article snapshot so a failed write-back can be retried. Download it before clearing the extension's local data or uninstalling. The saved question, answer and default source account also use `chrome.storage.local` with trusted-context access only. Personal answers and account numbers are not hardcoded in the extension source or download ZIP.

Exports contain private recipient and compensation details; keep them private. They are snapshots: check current unpaid records before using them. The session checklist cannot prevent duplicates after restart or across staff members. Contact checks are refreshed again during one-click preparation.

The extension uses visible DOM controls, not bank APIs. Vancity layout changes or sign-in prompts can stop automation. Use the normal bank interface if a screen is unsupported. Prepare can save a real missing recipient; it does not move funds or submit a payment.
